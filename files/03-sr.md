# Текущее состояние системы

## Статус системы P&R на текущем этапе

P&R развивается постепенно. Описание механизма в документации само по себе не означает, что механизм уже реализован и используется.

На текущем этапе необходимо различать:

1. **Работает** — механизм реально используется в повседневной жизни.
2. **Эксперимент** — механизм уже реализуется и проверяется на практике.
3. **Будущее** — идея или механизм, который пока не внедряется.
4. **Не работает** — механизм был опробован, но не дал требуемого результата.
5. **Мёртвый груз** — элемент существует только в документации и не выполняет полезной функции.

В настоящее время в качестве технической реализации используются только:
- Google-таблица (все нижеупомянутые листы относятся к ней)
- Google-календарь
- Расписание в личном кабинете учебного центра "Специалист" (ЛК УЧ "Специалист")

## 2. Регулярные действия

**Основной подход:** организация действий в группы и блоки.
см. файл 05-cw.md

**Действие** - конкретное рутинное действие, максимально простое.
**Группа действий** - набор рутинных действий, требуется фиксировать время окончания выполнения группы действий.
**Блок действий** - единый или разделённый на группы блок задач, который отнесён к определённому времени суток. 

**Основная задача блоков** - задействовать максимально работающие мотивационные механизмы (см. файл life-management-2026-09-17.md).

Блок задач может включать задачи, относящиеся к разным ролям.

**Правило отнесения блока к роли:**

Если блок состоит из нескольких неразрывно связанных действий, относящихся к разным ролям, блок относится к той роли, для которой выполнение всего блока в целом является способом достижения её основного результата.

Для выбора роли-владельца дополнительно можно использовать вопросы:

1. Для достижения какого результата какой роли предназначен блок в целом?
2. Если убрать весь блок, какой роли будет нанесён наибольший ущерб?

Отдельные задачи внутри блока при этом могут обеспечивать результаты других ролей.

### Иерархия работы P&R
Текущая модель:

> **Initiative → Epic → Task → Action**


* приоритизация задач;
* общий список задач;
* Sprint;
* выделение задач текущего Sprint;
* ежедневное планирование;
* фиксация фактически выполненных действий в `Actions`;
* связь `Task → Action`;
* возможность связывать Action непосредственно с Epic;
* возможность фиксировать Action без заранее заданной задачи;


### Приоритет задач
В основу приоритизации задач взят принцип Байана Трейси (Brian Tracy): каждая задача получает базовый приоритет ABCDE: 
- **A** — очень важные задачи; невыполнение имеет серьёзные последствия.
- **B** — задачи, которые желательно выполнить; последствия невыполнения небольшие.
- **C** — задачи, которые было бы хорошо выполнить, но невыполнение не имеет существенных последствий.
- **D** — задачи, которые следует делегировать.
- **E** — задачи, которые следует устранить.

ABCDE используется как **временный ручной механизм приоритизации**, пока не разработана и не проверена автоматическая модель вычисления приоритета задачи.
ABCDE не является окончательной архитектурой приоритизации P&R.

Сейчас в качестве временной формулы для Priority Score взята следующая:
PF (priority final) 
=IF(H2="Done"; 999; IF(E2="A";100;IF(E2="B";200;IF(E2="C";300;IF(E2="D";500;IF(E2="E";1000;-1000))))) +IFS(F2="";20;F2-TODAY()-G2/8<0;-200;F2-TODAY()-G2/8=0;-100;F2-TODAY()-G2/8<=2;-50;F2-TODAY()-G2/8<=7;-25;TRUE;0))

Если задача выполнена - приоритет (т.к. он уже не имеет смысла).
Иначе: базовый приоритет 100 / 200 / 300 / 500 / 1000 - для ABCDE (если базовый приоритет не задан, то -1000, чтобы задача всплыла наверх для обработки)
плюс поправка на дедлайн: чем ближе дедлайн, тем выше задачу надо поднять.

#### Вычисляемый приоритет задач

Долгосрочная цель системы приоритизации P&R — не ручное распределение всех задач по категориям, а автоматическое определение порядка выполнения.

Каждая задача должна иметь набор свойств, влияющих на её приоритет.

Потенциальные свойства:

- дедлайн;
- последствия невыполнения;
- значение для роли;
- вклад в актуальные результаты;
- срочность;
- размер задачи;
- зависимости от других задач;
- возможность выполнить задачу сейчас;
- и другие факторы, которые будут выявлены экспериментально.

В перспективе система должна вычислять:

> **Priority Score = f(свойства задачи)**

После этого задачи можно автоматически упорядочивать по финальному приоритету.

Таким образом, ABCDE является не конечной моделью приоритета, а временным пользовательским интерфейсом для ручного управления очередностью задач до появления вычисляемого Priority Score.

#### Архитектура приоритизации P&R

В P&R предполагается следующая долгосрочная архитектура:

> **Большой Backlog → свойства каждой задачи → вычисляемый приоритет → упорядоченная очередь задач**

Каждая задача потенциально обладает набором свойств, которые могут влиять на её приоритет:

- дедлайн;
- последствия невыполнения;
- значение для роли;
- вклад в актуальные результаты;
- срочность;
- размер;
- зависимости;
- возможность выполнения сейчас;
- и другие свойства, которые будут выявлены в ходе экспериментов.

На основе этих свойств в будущем должна вычисляться числовая величина:

> **Priority Score = f(свойства задачи)**

После этого задачи могут автоматически упорядочиваться по Priority Score.


### Sprint

Общий список задач является Backlog.

Для работы на ограниченном периоде из Backlog формируется отдельный Sprint.

Большой Backlog не является ежедневным рабочим списком.

В течение Sprint основная работа ведётся с выбранным набором задач Sprint.

### Actions

`Actions` предназначен для фиксации того, что фактически было сделано.

Основная задача текущего этапа:

> **не потерять информацию о реально совершённых действиях и использовать её для последующего анализа и планирования.**

Action может быть связан:

* с Task;
* с Epic;
* либо не иметь связи с заранее существовавшей задачей или Epic.

На практике большая часть действий в текущей системе оказывается связана с задачами.

### Results

`Results` пока не является обязательным рабочим механизмом.

Закладка/лист `Results` сохраняется как задел для дальнейшего развития системы.

В перспективе Results может использоваться для фиксации значимых результатов, в том числе при завершении Sprint или во время Review.

Пока не требуется регистрировать Result после каждого Action.

### Связь Epic / Task / Action

На текущем этапе используется следующая модель:

> **Epic → Task → Action**

Однако Action не обязан иметь Task:

> **Epic → Action**

или:

> **Action**

если действие было незапланированным и не относилось к существующему Epic или Task.

Связь `Epic/Task → Action` не должна рассматриваться как жёсткая последовательность заранее запланированных действий.

План описывает намерение, а не обязанность воспроизвести заранее известную последовательность действий.

В процессе выполнения задачи фактические действия могут отличаться от первоначального плана.

Задача также может изменяться после получения новой информации.

На текущем этапе P&R не требует отдельного хранения истории редактирования задач.

Если формулировка незавершённой задачи изменилась вследствие полученной информации, задача может быть отредактирована.

При этом уже записанные Actions сохраняются и продолжают ссылаться на ту задачу, с которой они были связаны на момент выполнения.

### Текущий фокус развития

Сейчас главная задача P&R — не анализировать отклонения фактических действий от первоначального плана.

Главная задача:

> **научиться надёжно фиксировать фактически совершённые действия и не терять информацию о том, что реально было сделано.**

Поэтому на текущем этапе:

* не требуется обязательная фиксация каждого результата;
* не требуется анализировать каждое отклонение от плана;
* не требуется восстанавливать полную историю изменения задач;
* не требуется связывать каждое действие с заранее существовавшей задачей;
* не требуется создавать сложную систему учёта.

Сначала необходимо накопить реальный массив данных о действиях.

В дальнейшем эти данные могут использоваться для:

* анализа поведения;
* планирования следующих действий;
* анализа связи между условиями, действиями и результатами;
* поиска закономерностей, например между сном, физической активностью, условиями дня и эффективностью работы.

# Sprint

Общий Backlog содержит задачи, которые потенциально могут быть выполнены.

Sprint является ограниченным рабочим набором задач на конкретный период.

В начале Sprint из Backlog выбираются задачи, которые предполагается выполнять в течение Sprint.

При этом выбор задач Sprint не означает, что первоначальный список является неизменным обязательством.

По мере получения новой информации задачи могут:

* уточняться;
* изменяться;
* разбиваться;
* заменяться;
* переноситься;
* становиться ненужными;
* дополняться новыми задачами.

Sprint нужен прежде всего для того, чтобы ограничить объём текущей работы и не заставлять человека ежедневно работать с огромным общим Backlog.

# Восстановление системы - ИСХОДНЫЙ ФАЙЛ

## Цель

Восстановить разработанную ранее систему управления жизнью, вернуть её к практическому применению и проверить её на устойчивость без преждевременного усложнения.

## Что необходимо восстановить

1. Текущий алгоритм работы.
2. Систему постановки целей на выбранном горизонте.
3. Подход к формулированию результатов по ролям.
4. Подход к переходу от целей к конкретным действиям.
5. Систему планирования.
6. Систему ежедневного учёта.
7. Систему баллов.
8. Правила анализа результатов и корректировки системы.
9. Способ возвращения к выбранным приоритетам после срыва.

## Принцип восстановления

Сначала восстановить то, что уже было разработано и опробовано в предыдущей работе, и только после этого вносить новые изменения.

Не усложнять систему, пока не восстановлена стабильная практика её применения.

> **Восстановление системы не должно становиться заменой реальному улучшению жизни.**

## План восстановления

1. Восстановить ранее разработанную систему целей и действий.
2. Восстановить систему планирования.
3. Восстановить систему ежедневного учёта и баллов.
4. Определить, какие элементы системы действительно нужны на текущем этапе.
5. Отдельно определить минимальный способ возвращения к приоритетам после срыва.
6. Провести короткий практический эксперимент.
7. Проанализировать результаты.
8. При необходимости скорректировать систему.

# Учёт баллов

| Обозначение | Название                                  | Определение |
| ----------- | --------------------- | --------------- |
| **I**       | **Importance — важность**                 | Насколько значим результат этого действия для моих важных целей/ролей. Оценивается от 1 до 5.                                                                                                      |
| **D**       | **Difficulty — трудность**                | Насколько трудно выполнить действие. Оценивается от 1 до 5.                                                                                                                                        |
| **N**       | **Novelty — новизна**                     | Насколько новым для меня является действие или способ его выполнения. Оценивается от 0 до 3.                                                                                                       |
| **Б₀**      | **Базовые баллы**                         | Баллы действия до учёта длительности, продуктивности и уместности. Сейчас рассчитываются по формуле `Б₀ = I + D + I×D + N`.                                                                        |
| **Время**   | **Время действия**                        | Фактически затраченное на действие время, включая технические перерывы.                                                                                                                            |
| **T**       | **Time — количество помидорок**           | Количество 30-минутных единиц времени, использованных действием.                                                                                                                                   |
| **P**       | **Productivity — продуктивность**         | Насколько продуктивно было использовано время длительного действия. 1,0 = 100% продуктивности.                                                                                                     |
| **C**       | **Current relevance / уместность сейчас** | Насколько правильным было выполнить это действие именно в данный момент. Сейчас оценивается вручную. 1,0 = полностью уместно; меньше 1,0 = действие стоило отложить ради более важных текущих дел. |

**Важное уточнение:** `C` — это не «важность» и не «срочность». Это именно **качество выбора момента**.

Баллы начисляются только действиям, которые я сознательно признал полезными/нужными.
Баллы начисляются за результат действия, а не за намерение.
Баллы  не мера объективной полезности дела.
Баллы  мера того, насколько хорошим выбором было выполнить это действие именно сейчас.
Важность действия оценивается от 1 до 5. Действия с важностью 0 не включаются в систему.
Трудность и новизна оцениваются до выполнения действия, чтобы не завышать их задним числом.
**Базовые баллы: Б₀ = I + D + I×D + N.**
**Двойная помидорка = 2 одинарные помидорки ≈ 1 час.**
**T = ⌈время / 25 мин⌉.**
Для действий длительностью не более одной двойной помидорки:

> **Б = Б₀.**

Для действий длительностью более одной двойной помидорки:
> **Б = Б₀ × (T / 2) × P**

где **P**  продуктивность, **0 < P ≤ 1**.
**P оценивается только для всего длительного действия, а не для каждой помидорки.**
Неполная одинарная помидорка считается полной.
Для действий, не требующих расхода времени, продуктивность не учитывается:
> **Б = Б₀.**

Плановость действия учитывается отдельно и не влияет на количество баллов.
Система баллов является экспериментальной и может изменяться после анализа результатов эксперимента.

## 1. Управляющий жизнью

**Желаемое поведение:**

> Ежедневно выделять время на размышление, планирование, контроль, корректировку и учёт.

## 2. Управляющий здоровьем

**Желаемые результаты:**

1. Снизить вес на 5 кг.
2. Уменьшить окружность живота.
3. Посетить терапевта.
4. Посетить дерматолога.
5. Посетить хирурга по поводу варикозного расширения вен.

**Желаемое поведение:**

1. Соблюдать режим сна.
2. Гулять каждый день 1 час или дольше.
3. Ходить в бассейн 4 раза в неделю.

**Текущая ситуация:**

* Точный текущий вес неизвестен; ориентировочно 165 кг. Весы должны быть получены 3 сентября 2026 года.
* Окружность живота не измерялась.
* Режим сна крайне хаотичный: бывают бессонные ночи, дневной сон, отход ко сну в разное время.
* Физическая активность очень низкая; иногда несколько дней не выходить из дома.
* Ходьба  примерно несколько часов в неделю или меньше.
* В бассейне не был около 3 месяцев.
* Питание: много сладкого и жирного, переедание; финансовые ограничения способствуют покупке дешёвых и менее качественных продуктов.
* Терапевт  примерно год назад.
* Дерматолог  примерно год назад.
* Есть варикозное расширение вен и направление к хирургу.

## 3. Финансовый обеспечитель

**Желаемый результат:**

1. Получить хотя бы одно предложение о работе.

**Промежуточный показатель:**

2. Пройти не менее 3 собеседований.

**Желаемое поведение:**

1. Ежедневно выделять время на проверку домашних заданий.
2. Выделять время на написание новых курсов.
3. Выделять время на поиск новой работы.
4. Выделять время на обучение ИИ.
5. Выделять время на другое желательное обучение.

**Что должно быть сделано:**

1. Закрыть долги по проверке домашних заданий  примерно 10 работ, около 5 часов работы.
2. Обновить резюме.
3. Начать поиск работы.
4. Изучить что-либо про ИИ.

**Текущая ситуация:**

* Текущая работа  преподаватель в УЦ «Специалист».
* Текущая занятость  примерно 1/5 полного рабочего дня, около 8–16 часов в неделю.
* Требуется найти работу на полный рабочий день; дальнейшая нагрузка будет оцениваться после устройства.
* Желаемая должность  руководитель команды тестирования ПО.
* Опыт в тестировании  более 20 лет.
* Резюме есть, обновлялось около года назад.
* Поиск работы в последний месяц не велся.
* Есть подходящие вакансии.
* Есть около 10 непроверенных домашних заданий, примерно 5 часов работы.
* Проверка домашних заданий  обязательно.
* Новые курсы, поиск работы, обучение ИИ и другое обучение  желательно.

## 4. Ведущий хозяйство

**Желаемый результат:**

К концу месяца в квартире комфортно жить:

1. Чистый ковёр и пол.
2. Порядок в комнате.
3. Порядок на кухне, вся посуда чистая.
4. Всё грязное бельё перестирано.
5. Создана работающая рутина закупки продуктов и приготовления еды.

**Желаемое поведение:**

1. Регулярно выделять время на пылесос, мытьё полов и вытирание пыли.
2. Регулярно выделять время на закупку качественных продуктов.
3. Регулярно выделять время на приготовление еды.

**Текущая ситуация:**

| Область           | Текущее состояние |
| ----------------- | ----------------: |
| Ковёр             |              2/10 |
| Пол               |              2/10 |
| Комната           |              3/10 |
| Кухня             |              3/10 |
| Посуда            |              4/10 |
| Грязное бельё     |              4/10 |
| Закупка продуктов |              1/10 |
| Приготовление еды |              1/10 |

**Выявленные препятствия:**

* Лень / отсутствие достаточного побуждения к бытовым действиям.
* Одиночество: ранее наличие жены или приглашённых гостей создавало внешний стимул поддерживать порядок.
