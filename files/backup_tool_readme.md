
# backup_tool_readme.md


# Backup Tool — README

Локальное приложение на Python для ручного резервного архивирования
текстовых файлов (Markdown, JSON и др.), а также файлов с расширениями
из `binary_meta_extensions` (по умолчанию `.xlsx`, `.xlsm`), и подготовки
scp-команды для выгрузки на сервер.

---

## 1. Назначение программы

Приложение решает три задачи:

1. **Резервное копирование.** Раз в некоторое время (обычно раз в сутки)
   вы запускаете программу, она смотрит, какие файлы в рабочей папке
   сильно изменились с момента последнего архивирования, и складывает
   вчерашнюю версию в подпапку `archive\`.
2. **Чистка архива.** Из `archive\` всегда оставляется только самый
   свежий архив каждого файла; более старые архивы целиком переезжают
   в `archive\old\`. Это позволяет визуально сравнить «что было вчера»
   с «что сейчас» через любой файловый менеджер (в том числе с телефона
   через Яндекс.Диск).
3. **Выгрузка на сервер.** По накопленным архивам формируется одна
   длинная команда `scp`, которой можно одной вставкой в терминале
   скопировать на сервер все файлы, изменившиеся с момента предыдущей
   выгрузки.

Приложение работает **локально**, ничего никуда не отправляет, ничего
не удаляет из рабочей папки и не вызывает `scp` — только формирует
строку команды.

## 2. Бизнес-правила (требования)

### 2.1. Списки типов файлов

- Программа хранит два списка расширений: **обрабатываемые** и **игнорируемые**.
- Оба списка редактируются вручную в UI: два `Listbox` со стрелочками `→` / `←`
  для перемещения выделенных элементов.
- В конфиге хранятся **только те расширения, которые реально присутствуют
  в рабочей папке**. Если файлов с каким-то расширением больше нет — оно
  автоматически исчезает из обоих списков при очередном сканировании.

### 2.2. Появление новых типов

- При каждом запуске (и по кнопке «Сканировать папку») программа
  перебирает все расширения в рабочей папке и сравнивает с теми, что
  уже в списках.
- **По умолчанию новое расширение считается не обрабатываемым.** Программа
  спрашивает диалогом: «Обнаружен новый тип файлов: `<ext>`. Добавить его
  в обрабатываемые?».
  - «Да» → `tracked_extensions`.
  - «Нет» → `ignored_extensions`.

### 2.3. Списки файлов

- Внутри обрабатываемых расширений программа хранит два списка имён файлов:
  **обрабатываемые** и **игнорируемые**.
- Редактируются так же — два `Listbox` со стрелочками.
- При появлении нового файла с обрабатываемым расширением программа
  спрашивает: «Обнаружен новый файл: `<имя>`. Добавить его в обрабатываемые?».
  **По умолчанию файл не обрабатывается, пока пользователь явно не согласился.**
- Файлы с игнорируемыми расширениями в этот список вообще не попадают.

### 2.4. Сравнение двух версий файла

- **Текстовые файлы** (все, кроме перечисленных в
  `binary_meta_extensions`):
  - сравниваются непустые строки. Строки, состоящие только из пробелов
    и табуляций, а также пустые строки, **игнорируются**;
  - хвостовые пробелы и табуляции у каждой строки тоже отбрасываются;
  - метрика различий — число несовпавших непустых строк. Для каждого
    блока различий берётся `max(удалённых, добавленных)`, результаты
    суммируются.
- **Файлы из `binary_meta_extensions`** (по умолчанию `.xlsx`, `.xlsm`):
  содержимое **не читается**. Сравниваются **метаданные** — размер
  файла и время последнего изменения (mtime). Файл считается изменённым,
  если хотя бы одно из этих значений отличается от соответствующего
  значения самого свежего архива. Причина — формат `.xlsx` является
  ZIP-контейнером, а не текстом, и построчное сравнение к нему
  неприменимо.
- **Git не используется.** Источник «старой» версии — самый свежий
  архивный файл для данного файла в `archive\`. Если архива нет, файл
  считается «сильно изменённым» (это первичный бэкап).

### 2.5. Пороги «сильного изменения»

- В конфиге два независимых параметра:
  - `threshold` — целое ≥ 0, порог по числу несовпавших непустых строк;
  - `force_archive_after_days` — целое ≥ 0, порог по числу дней с даты
    самого свежего архива.
- **Текстовый файл** считается «сильно изменённым» (и подлежит
  архивированию при обычном нажатии кнопки «Выполнить добавление
  в архив изменившихся файлов»), если выполнено **любое** из условий:
  - число несовпавших непустых строк ≥ `threshold`; **или**
  - число несовпавших непустых строк ≥ 1 **и** прошло ≥
    `force_archive_after_days` дней с даты самого свежего архива.
- Файл с нулём нетривиальных изменений (только пустые строки, пробелы,
  табуляции) не архивируется **никогда** — вне зависимости от давности.
- **Для файлов из `binary_meta_extensions`** порог `threshold`
  **не применяется**: метрика бинарная («изменён» / «не изменён»).
  Порог `force_archive_after_days` тоже не имеет смысла: если файл
  изменился — он архивируется сразу; если нет — то и по дням его
  архивировать не за что.
- Значения по умолчанию — `threshold = 10`,
  `force_archive_after_days = 7`, `binary_meta_extensions = [".xlsx",
  ".xlsm"]`. Задаются **только** в конфиге (и через вкладку
  «Настройки» — для первых двух), в коде бизнес-логики ничего
  не зашито.

**Пример.** Порог `threshold = 10`, `force_archive_after_days = 7`.
Файл `01-roles.md` последний раз архивировался `2026-09-15`, сегодня
`2026-09-22`. Пользователь изменил 3 непустые строки. Изменений
меньше порога (3 < 10), но с архива прошло 7 дней (≥ 7), поэтому файл
будет заархивирован.

### 2.6. Правила архивирования

- Запускается вручную с вкладки «Архивирование» одной из двух кнопок
  (см. 2.6.1 и 2.6.2 ниже).
- Для каждого обрабатываемого файла:
  - если он «сильно изменён» по правилам раздела 2.5 — копия кладётся
    в `archive\<base>-<вчера>.ext` (вчерашняя дата, `YYYY-MM-DD`
    от системной даты);
  - если файл с таким именем и датой уже есть в `archive\` —
    **копирование не производится** (файл продолжает активно
    меняться, ждём, пока он «устоится»);
  - если изменений ниже обоих порогов — ничего не делается;
  - если нетривиальных изменений нет вообще — ничего не делается.
- После копирования — **чистка архива**: для каждого файла в `archive\`
  остаётся только один самый свежий архив, все прочие **целиком**
  переносятся в `archive\old\`.

#### 2.6.1. Обычный режим: «Выполнить добавление в архив изменившихся файлов»

- Использует оба порога: `threshold` **или** `force_archive_after_days`.
- Архивирует только то, что «сильно изменилось» по правилам 2.5.

#### 2.6.2. Режим «Архивировать все изменённые»

- Игнорирует **оба** порога.
- Архивирует **все** tracked-файлы, у которых число несовпавших
  непустых строк ≥ 1 (для текстовых) или у которых разошлись
  метаданные (для файлов из `binary_meta_extensions`).
- Файлы без изменений и файлы, для которых архив с датой «вчера»
  уже существует, по-прежнему пропускаются.
- Используется, когда надо одним нажатием зафиксировать любые
  правки, не дожидаясь порогов.

### 2.7. Журнал выгрузок на сервер

- Для каждого файла в конфиге хранится дата последней выгрузки
  на сервер (`server_upload_log`).
- Считается, что файл нужно выгрузить, если **дата самого свежего архива
  больше даты последней выгрузки** (или выгрузки ещё не было).
- Исходные файлы при этом не трогаются и не читаются — только имена
  в `archive\` и даты в журнале.

### 2.8. Формирование scp-команды

- Формируется **одна** строка вида:
  ```
  scp <файл1> <файл2> ... <user>@<host>:<remote_base>/<сегодня>/
  ```
- Дата в удалённом пути — **сегодняшняя**.
- `scp` **не вызывается**, команда копируется вручную.
- Комментарии-строки (начинаются с `#`) — просто информация, их
  копировать не надо.

### 2.9. Логирование

- Файловые логи не ведутся.
- Ход архивирования выводится в текстовое поле на вкладке «Архивирование».
- Ошибки, при которых действие невозможно, показываются диалогом.

### 2.10. Разделение отчёта по категориям

После нажатия любой из двух кнопок архивирования отчёт в логе
разбит на секции, чтобы сразу видеть, что произошло с каждым файлом:

1. **`[1] Заархивировано`** — список файлов, для которых архив
   реально создан. По каждому указано число изменений и причина
   (например, «изменений 12 ≥ порога 10» или «изменений 3 (ниже
   порога 10), но 7 дн. с архива ≥ 7», а для `.xlsx` — «изменён
   по метаданным (размер `A` → `B`, mtime `X` → `Y`)»).
2. **`[2] Сильно изменены, но архив с датой <вчера> уже есть —
   пропуск`** — файлы, которые опять сильно изменились, но вчера
   их уже архивировали (значит, файл продолжает активно меняться —
   второй раз за сутки его архивировать смысла нет).
3. **`[3] Изменения ниже порога — пропуск`** — текстовые файлы,
   где изменений мало и давность с архива ещё не превышена. Указано
   число изменений, порог, число дней с архива и порог дней. Для
   `.xlsx` эта секция не используется.
4. **`[4] Без значимых изменений`** — файлы, у которых либо после
   нормализации (удаления пустых строк, пробелов, табуляций)
   несовпавших строк не осталось вообще, либо у которых совпали
   метаданные (для `.xlsx`). Указана дата текущего свежего архива.
5. **`[5] Файлы отсутствуют или не читаются`** — если что-то
   пропало из папки или не открылось.
6. **`[!] Ошибки`** — если что-то пошло не так на этапе копирования
   или чтения архива.

Секции `[1]`–`[4]` выводятся всегда (с `: 0`, если пусто). Секции `[5]`
и `[!]` печатаются только при наличии содержимого. В конце — строка
«Перемещено в old: N».

## 3. Установка и первый запуск (Windows)

### 3.1. Проверка Python

1. Откройте `cmd` (`Win + R` → `cmd`).
2. Выполните:
   ```
   python --version
   ```
3. Должно вывести `Python 3.10` или новее. Проверено на 3.13.5.
4. Если команда не найдена — установите Python с
   https://www.python.org/downloads/windows/ и **обязательно** поставьте
   галочку «Add python.exe to PATH».

Дополнительные библиотеки не нужны — всё в стандартной поставке.
Файлы `.xlsx` обрабатываются без чтения содержимого (сравнение
по метаданным), поэтому `openpyxl` и другие пакеты не требуются.

### 3.2. Раскладка файлов

```
E:\YandexDisk\slqa\pr\files\
├── backup_tool.pyw            ← приложение
├── backup_tool_config.json    ← создастся при первом запуске
├── 00-prompt.md
├── 01-roles.md
├── ...
└── archive\
    └── old\
```

Папку `archive\old\` создавать вручную не обязательно — приложение
сделает это само.

### 3.3. Поиск `pythonw.exe` (если Windows не знает, чем открыть `.pyw`)

Откройте `cmd` и выполните:

```
where pythonw
```

Ожидаемый вывод (пример):

```
C:\Python313\pythonw.exe
```

Если `where pythonw` ничего не нашёл, но `python --version` работает:

```
where python
```

и замените в выводе `python.exe` на `pythonw.exe` в той же папке.
Альтернативный способ — выполнить в `cmd`:

```
python -c "import sys, os; print(os.path.dirname(sys.executable))"
```

и посмотреть на содержимое этой папки в Проводнике.

### 3.4. Привязка `.pyw` к `pythonw.exe`

1. Правый клик по `backup_tool.pyw` → «Открыть с помощью» →
   «Выбрать другое приложение».
2. В диалоге — «Найти другое приложение на этом компьютере» (или «Обзор»).
3. Введите полный путь к `pythonw.exe` (например, `C:\Python313\pythonw.exe`).
4. Поставьте галочку «Всегда использовать это приложение для открытия
   `.pyw` файлов».
5. ОК.

Если диалог не даёт выбрать или не сохраняет галочку — запустите `cmd`
**от имени администратора** и выполните:

```
ftype Python.NoConFile="C:\Python313\pythonw.exe" "%1" %*
assoc .pyw=Python.NoConFile
```

Если `assoc .pyw=...` ответит «Отказано в доступе», сбросьте привязку:

```
assoc .pyw=
assoc .pyw=Python.NoConFile
```

### 3.5. Ярлык на рабочем столе (по желанию)

Правый клик по `backup_tool.pyw` → «Отправить» → «Рабочий стол
(создать ярлык)». Переименуйте в «Backup Tool».

### 3.6. Первый запуск

1. Двойной клик по `backup_tool.pyw`.
2. Рядом появится `backup_tool_config.json` со значениями по умолчанию.
   Поле `folder` уже указывает на папку, где лежит сам `.pyw`.
3. Сразу после открытия программа просканирует папку. По каждому
   новому расширению и каждому новому файлу с обрабатываемым расширением
   спросит: «Добавить в обрабатываемые?». Ответьте.
4. Откройте вкладку «Настройки», проверьте `folder`, `threshold`,
   `force_archive_after_days`, параметры сервера. Нажмите «Сохранить
   настройки».

Готово. Можно переходить к ежедневной работе.

## 4. Формат конфига

Файл `backup_tool_config.json` — JSON в UTF-8, читается и пишется
приложением при каждом изменении настроек. Можно редактировать
вручную — при следующем запуске значения подхватятся.

```json
{
  "folder": "E:\\YandexDisk\\slqa\\pr\\files",
  "archive_subfolder": "archive",
  "archive_old_subfolder": "old",
  "tracked_extensions": [".md", ".json", ".xlsx"],
  "ignored_extensions": [".pyw"],
  "tracked_files": [
    "01-prompt.md",
    "02-main.md",
    "03-regular.md",
    "pr-dashboard.xlsx"
  ],
  "ignored_files": [
    "backup_tool_config.json",
    "backup_tool_readme.md"
  ],
  "threshold": 10,
  "force_archive_after_days": 7,
  "binary_meta_extensions": [".xlsx", ".xlsm"],
  "server_upload_log": {
    "01-prompt.md": "2026-09-25"
  },
  "server": {
    "user": "slqamsk",
    "host": "193.37.70.210",
    "remote_base": "~/Downloads"
  }
}
```

### Поля

| Поле | Тип | Назначение |
|------|-----|------------|
| `folder` | строка | Абсолютный путь к рабочей папке. Обычно папка, где лежит `.pyw`. |
| `archive_subfolder` | строка | Имя подпапки архива. По умолчанию `archive`. |
| `archive_old_subfolder` | строка | Имя подпапки старых архивов внутри `archive`. По умолчанию `old`. |
| `tracked_extensions` | массив строк | Обрабатываемые расширения (с точкой, в нижнем регистре). Только те, что есть в папке. |
| `ignored_extensions` | массив строк | Игнорируемые расширения. |
| `tracked_files` | массив строк | Обрабатываемые файлы (только имена, без пути). |
| `ignored_files` | массив строк | Игнорируемые файлы. |
| `threshold` | целое ≥ 0 | Порог числа несовпавших непустых строк. Если изменений меньше — файл при обычном архивировании пропускается (кроме случая `force_archive_after_days`). Для файлов из `binary_meta_extensions` не применяется. |
| `force_archive_after_days` | целое ≥ 0 | Если с даты самого свежего архива прошло ≥ N дней и есть хотя бы одно нетривиальное изменение — файл архивируется даже при изменениях ниже `threshold`. Для файлов из `binary_meta_extensions` не применяется. |
| `binary_meta_extensions` | массив строк | Расширения файлов, которые сравниваются по метаданным (размер + mtime), без чтения содержимого. По умолчанию `[".xlsx", ".xlsm"]`. Порог `threshold` для них не применяется. |
| `server_upload_log` | объект | «имя файла → дата последней выгрузки» в формате `YYYY-MM-DD`. |
| `server.user` | строка | SSH-пользователь для `scp`. |
| `server.host` | строка | Хост/IP сервера. |
| `server.remote_base` | строка | Базовая папка на сервере; дата добавляется к ней. |

### Что можно править руками

- **Всё.** Если что-то сломается — удалите файл, при следующем запуске
  создастся заново с дефолтами (журнал `server_upload_log` и списки
  файлов будут потеряны).
- `binary_meta_extensions` можно расширять — например, добавить
  `.docx`, `.pptx`, `.odt`, если они начнут обрабатываться. Список
  не привязан к `.xlsx` жёстко.
- Пути в `folder` на Windows можно писать и через `\\`, и через `/`.
- Порядок элементов в списках значения не имеет.

## 5. Инструкция пользователя

### 5.1. Ежедневный сценарий

1. Двойной клик по ярлыку «Backup Tool».
2. Если появились диалоги «Обнаружен новый тип / новый файл» — ответьте.
3. Вкладка **«Архивирование»** → кнопка **«Выполнить добавление в архив
   изменившихся файлов»**. Посмотрите лог: что заархивировано, что ушло
   в `old/`, что пропущено.
4. Вкладка **«Выгрузка на сервер»** → кнопка **«Сформировать команду
   выгрузки»**. В верхнем поле появится строка `scp ...`.
5. Нажмите **«Скопировать команду»** — она окажется в буфере обмена.
6. Откройте терминал (`cmd`, PowerShell или Git Bash), при необходимости
   создайте папку на сервере:
   ```
   ssh slqamsk@193.37.70.210 "mkdir -p ~/Downloads/2026-09-25"
   ```
   Вставьте команду (`Ctrl+V`) и выполните.
7. Вернитесь в приложение → кнопка **«Отметить выгрузку выполненной»**.
   Даты в журнале обновятся — при следующем запуске уже выгруженные
   файлы в команду не попадут.

### 5.2. Вкладка «Типы файлов»

- Слева — обрабатываемые расширения, справа — игнорируемые.
- Выделите один или несколько элементов (`Shift` / `Ctrl` для множественного
  выделения) и нажмите `→` или `←`, чтобы переместить.
- Кнопка «Сканировать папку» — обновить списки по фактическому содержимому
  и ответить на вопросы о новых типах.

### 5.3. Вкладка «Файлы»

- То же самое, но для конкретных имён файлов внутри обрабатываемых
  расширений.
- Если файл больше не нужен — перетащите его вправо; он останется
  в папке, но программа перестанет его архивировать и выгружать.

### 5.4. Вкладка «Настройки»

- **Папка с файлами** — путь к рабочей папке. Если папка не найдена,
  сканирование не сработает.
- **Порог изменений (непустых строк)** — целое число. При обычном
  архивировании файлы с изменениями ниже этого порога пропускаются
  (кроме случая, когда истёк срок `force_archive_after_days`). Для
  файлов из `binary_meta_extensions` этот порог не применяется.
- **Принудительно архивировать после N дней с последнего архива** —
  целое число. Если файл изменился (хотя бы на одну непустую строку),
  но изменений меньше `threshold`, и при этом с даты самого свежего
  архива прошло ≥ N дней — файл всё равно будет заархивирован. Для
  файлов из `binary_meta_extensions` не применяется.
- **Сервер** — `user`, `host`, `remote_base` (используются только при
  формировании команды, никаких сетевых вызовов).
- После правок — **«Сохранить настройки»**. При некорректных значениях
  (не число, отрицательное) сохранение отменяется с сообщением
  об ошибке.

### 5.5. Вкладка «Архивирование»

- Две кнопки и большое текстовое поле с логом.
- **«Выполнить добавление в архив изменившихся файлов»** — обычный
  режим. Архивирует файлы, у которых:
  - для текстовых: изменений ≥ `threshold`; **или** изменений ≥ 1
    и прошло ≥ `force_archive_after_days` дней с даты самого свежего
    архива;
  - для `.xlsx` (и других из `binary_meta_extensions`): разошлись
    метаданные (размер или mtime).
- **«Архивировать все изменённые»** — игнорирует оба порога.
  Архивирует любой файл, у которого есть хотя бы одно нетривиальное
  изменение (или разошлись метаданные для `.xlsx`). Файлы без изменений
  и уже заархивированные сегодня по-прежнему пропускаются.

Лог после нажатия разделён на секции:

1. `[1] Заархивировано` — что реально скопировано.
2. `[2] Сильно изменены, но архив с датой <вчера> уже есть — пропуск` —
   файл продолжает активно меняться.
3. `[3] Изменения ниже порога — пропуск` — с указанием числа изменений,
   порога, дней с архива и порога дней. Только для текстовых файлов.
4. `[4] Без значимых изменений` — либо изменения только в пустых
   строках и пробелах/табуляциях (для текстовых), либо метаданные
   совпали (для `.xlsx`).
5. `[5] Файлы отсутствуют или не читаются` — при необходимости.
6. `[!] Ошибки` — при необходимости.

Для файлов из `binary_meta_extensions` (например, `.xlsx`) в логе
вместо «изменений N» пишется «изменён по метаданным (размер `A` → `B`,
mtime `X` → `Y`)» — это видно в секциях `[1]` и `[2]`. В секции `[4]`
для них указывается «по метаданным без изменений» вместо «только
пустые строки / пробелы».

В конце — строка «Перемещено в old: N».

### 5.6. Вкладка «Выгрузка на сервер»

- Три кнопки и два поля:
  - **Команда для копирования** — верхнее поле, здесь только строка `scp`.
  - **Информация о файлах** — нижнее поле, строки с `#` для справки.
  - **Сформировать команду выгрузки** — заполнить оба поля.
  - **Скопировать команду** — положить строку `scp` в буфер обмена.
  - **Отметить выгрузку выполненной** — записать сегодняшнюю дату
    в журнал по всем файлам из сформированного списка.

### 5.7. Частые ситуации

- **Хочу пересобрать списки файлов с нуля.** Вкладка «Файлы» → перетащить
  всё вправо → «Сканировать папку» → ответить на диалоги заново.
- **Файл больше не нужен.** Перетащить в «Игнорируемые». Исходник
  в папке останется.
- **Случайно сломал конфиг.** Удалить `backup_tool_config.json` — при
  следующем запуске создастся заново. Журнал выгрузок и списки
  файлов будут потеряны.
- **Нужно сохранить конфиг на будущее.** Скопируйте
  `backup_tool_config.json` в надёжное место — он же хранит
  `server_upload_log`.
- **`.xlsx` архивируется слишком часто.** Это нормально, если Excel
  пересобирает файл при каждом сохранении, даже без реальных правок.
  Защита — архив с вчерашней датой уже существует, второй раз за сутки
  файл не копируется. Старые архивы уезжают в `old/`, места почти
  не занимают.

## 6. Как работает каждая операция (техническое описание)

Ниже — внутреннее устройство приложения, для отладки и понимания
поведения в нестандартных ситуациях.

### 6.1. Загрузка конфига (`load_config`)

1. Если файла `backup_tool_config.json` рядом с приложением нет —
   создаётся глубокая копия `DEFAULT_CONFIG`, сохраняется через
   `save_config` и возвращается как текущая.
2. Если файл есть — открывается, парсится как JSON, возвращается
   словарь. Дополнение недостающих ключей не делается: чего нет
   в конфиге — того нет и в программе.

### 6.2. Сохранение конфига (`save_config`)

- Полностью перезаписывает файл содержимым словаря `cfg`.
- Формат: UTF-8, `indent=2`, `ensure_ascii=False` (кириллица в путях
  сохраняется как есть).
- Вызывается: после любого перемещения в списках, после «Сканировать
  папку», после «Сохранить настройки», после «Отметить выгрузку
  выполненной».

### 6.3. Чтение текстового файла (`read_text_lines`)

1. Пытается открыть файл в текстовом режиме с кодировкой `utf-8`.
2. При `UnicodeDecodeError` — повторяет с `cp1251`.
3. При `OSError` — возвращает `None` (файл недоступен).
4. Если обе кодировки не подошли — `None`.
5. Возвращает список строк без символов конца строки (`.splitlines()`).

Вызывается **только** для текстовых файлов из `tracked_files`.
Для расширений из `binary_meta_extensions` не вызывается вообще.

### 6.4. Нормализация строк (`normalized_lines`)

1. Берёт результат `read_text_lines`. Если `None` — возвращает `None`.
2. Каждую строку приводит к виду `rstrip()` — убирает хвостовые пробелы
   и табуляции.
3. Выбрасывает строки, для которых `strip()` пуст — то есть пустые
   строки и строки только из пробелов, табуляций, `\r`, `\v`, `\f`.
4. Возвращает список оставшихся строк.

Именно поэтому добавление/удаление пустых строк и хвостовых пробелов
**не считается изменением**.

### 6.5. Метрика различий (`count_changed_lines`)

1. На вход — два нормализованных списка строк: старый (архив) и новый
   (текущий файл).
2. `difflib.SequenceMatcher(a=old, b=new, autojunk=False)` строит
   оптимальное выравнивание.
3. По опкодам (`get_opcodes()`) для блоков `replace`, `delete`, `insert`
   прибавляется `max(i2-i1, j2-j1)`.
4. Результат — целое число несовпавших непустых строк.

### 6.5.1. Подсчёт дней (`days_between`)

- Принимает дату архива в формате `YYYY-MM-DD` и (опционально)
  сегодняшнюю дату. По умолчанию вторая — `datetime.date.today()`.
- Возвращает разницу в днях: `today − date_str`.

### 6.5.2. Сравнение по метаданным (`is_binary_meta`, `binary_changed_info`, `fmt_mtime`)

- `is_binary_meta(cfg, name)` — берёт расширение файла и проверяет,
  входит ли оно в `cfg["binary_meta_extensions"]` (без учёта регистра).
- `binary_changed_info(cur_path, arch_path)` — сравнивает два файла
  по `os.path.getsize` и `os.path.getmtime`. Возвращает кортеж
  `(changed, size_cur, size_arch, mtime_cur, mtime_arch)`, где
  `changed = True`, если размер или mtime различаются.
- `fmt_mtime(ts)` — форматирует POSIX-время в `YYYY-MM-DD HH:MM:SS`
  для читаемого вывода в логе.

### 6.6. Поиск самого свежего архива (`find_newest_archive`)

- Из имени файла берётся `base` и `ext`.
- В папке `archive\` перебираются файлы, чьё имя строго соответствует
  шаблону `^<base>-YYYY-MM-DD<ext>$` (регулярка с `re.escape`).
- Среди подходящих выбирается с максимальной датой (лексикографически —
  работает, потому что формат ISO).
- Возвращает `(полный_путь, дата)` или `(None, None)`.
- Файлы источника не читаются, только имена в `archive\`.

### 6.7. Скан расширений (`scan_extensions`)

1. Проверяется существование `folder`.
2. `list_all_extensions(folder)` собирает множество всех расширений
   файлов в корне папки (без рекурсии).
3. Из `tracked_extensions` и `ignored_extensions` **удаляются те
   элементы, которых больше нет в папке**.
4. Для каждого найденного расширения, которого нет ни в одном списке,
   задаётся вопрос: «Добавить его в обрабатываемые?».
   - «Да» → `tracked_extensions`.
   - «Нет» → `ignored_extensions`.
5. Конфиг сохраняется, оба `Listbox` перерисовываются.

При старте вызывается со `silent=True` — сообщение «новых типов нет»
не показывается, но диалоги по каждому новому расширению всё равно идут.

### 6.8. Скан файлов (`scan_files`)

1. Проверяется существование папки.
2. Собирается множество расширений из `tracked_extensions`.
3. Перебираются все файлы в корне папки; отбираются те, чьё расширение
   входит в tracked и чьего имени нет ни в `tracked_files`,
   ни в `ignored_files`.
4. По каждому — диалог «Добавить в обрабатываемые?». «Да» →
   `tracked_files`, «Нет» → `ignored_files`.
5. Конфиг сохраняется, списки обновляются.

### 6.9. Перемещение элементов между списками (кнопки `→` / `←`)

- `DualList._move(src, dst)`:
  1. Собирает индексы всех выделенных элементов (поддерживается
     `selectmode="extended"` — множественное выделение).
  2. Собирает значения этих элементов.
  3. Удаляет их из источника **в обратном порядке**, чтобы индексы
     не съехали.
  4. Добавляет их в конец приёмника.
- После перемещения вызывается `on_change` → конфиг перезаписывается.

### 6.10. Сохранение настроек (`save_settings`)

1. Поле «Порог изменений» приводится к `int`. Если не число или
   отрицательное — сообщение об ошибке, ничего не сохраняется.
2. Поле «Принудительно архивировать после N дней» приводится к `int`.
   Проверка та же.
3. В `cfg` переносятся: `folder`, `threshold`,
   `force_archive_after_days`, `server.user`, `server.host`,
   `server.remote_base`. Ключ `binary_meta_extensions` **не
   редактируется через UI** — он задаётся только в конфиге вручную.
4. `save_config` → запись в JSON.
5. `refresh_lists()` — обновление списков (на случай смены `folder`).
6. Сообщение «Сохранено».

### 6.11. Архивирование (`do_archive`)

Вызывается кнопкой «Выполнить добавление в архив изменившихся файлов»
(режим `force_all=False`) или «Архивировать все изменённые»
(режим `force_all=True`). Для каждого имени из `tracked_files`
сначала определяется режим сравнения через `is_binary_meta(cfg, name)`:
если расширение входит в `binary_meta_extensions` — работаем по
метаданным, иначе по тексту.

**Для текстовых файлов:**

1. Проверка наличия файла. Нет — в `missing`.
2. Чтение текущего файла через `normalized_lines`. Если `None` —
   в `missing`.
3. `find_newest_archive` → (`path`, `arch_date`).
   - Архива нет — `need = True`, `info = "архива нет (первичный бэкап)"`.
   - Архив есть — читается через `normalized_lines`; если нечитаем —
     в `errors`. Иначе:
     - `changes = count_changed_lines(old, cur)`;
     - `days = days_between(arch_date)`;
     - `changes == 0` → в `unchanged` (info = «только пустые строки /
       пробелы»);
     - `force_all` → `need = True`, reason «есть изменения (режим
       "все изменённые")»;
     - `changes >= threshold` → `need = True`, reason «изменений N ≥
       порога T»;
     - `days >= force_days` → `need = True`, reason «изменений N
       (ниже порога T), но D дн. с архива ≥ F»;
     - иначе → в `below`, идёт дальше;
     - `info = "изменений N, " + reason`.

**Для файлов из `binary_meta_extensions`:**

1. Проверка наличия файла. Нет — в `missing`.
2. `find_newest_archive` → (`path`, `arch_date`).
   - Архива нет — `need = True`, `info = "архива нет (первичный
     бэкап, метаданные)"`.
   - Архив есть — `binary_changed_info(path, arch_path)`:
     сравниваются `os.path.getsize` и `os.path.getmtime` текущего
     файла и архива.
     - Если **оба** совпали → в `unchanged` (info = «по метаданным
       без изменений»).
     - Иначе → `need = True`, `info = "изменён по метаданным
       (размер A → B, mtime X → Y)"`. Пороги не применяются.

**Для обеих веток на выходе:**

- Формируется `target_name = <base>-<вчера>.ext`.
- Если такой файл в `archive\` уже есть → в `already`.
- Иначе `shutil.copy2` → в `archived`. `shutil.copy2` работает
  одинаково и для текстовых, и для `.xlsx` — бинарь копируется
  как есть.

**Отчёт** разбит на секции `[1]`–`[5]` и `[!]` (см. 2.10 и 5.5).
Секции `[1]`–`[4]` печатаются всегда, `[5]` и `[!]` — только при
наличии содержимого. После отчёта вызывается `cleanup_archives`.
Исходные файлы не изменяются и не удаляются.

### 6.12. Очистка `archive\` (`cleanup_archives`)

1. Создаётся `archive\old\` (если нет).
2. Для каждого имени из `cfg["tracked_files"]`:
   - Строится регулярка `^<base>-YYYY-MM-DD<ext>$`.
   - Собираются все подходящие файлы в `archive\`.
3. Если файлов ≤ 1 — группа не трогается.
4. Если больше:
   - Сортировка по дате **по убыванию**.
   - Первый (самый свежий) остаётся в `archive\`.
   - Остальные `shutil.move` → `archive\old\`. При конфликте имён
     добавляется суффикс `__1`, `__2`, ... до свободного.
5. Возвращает число перемещённых. В лог — строка на каждый перенос.

Итог: в `archive\` для каждого файла — ровно **один** самый свежий
архив; все прочие — в `archive\old\`.

### 6.13. Формирование scp-команды (`generate_upload`)

1. Читается `server_upload_log` и `tracked_files`.
2. Для каждого tracked-файла:
   - `find_newest_archive` → (`path`, `arch_date`).
   - Архива нет — пропуск.
   - `arch_date > last_upload_date` (или записи о выгрузке ещё нет) —
     файл попадает в список на выгрузку.
3. Исходные файлы не читаются — только имена в `archive\`
   и даты в журнале.
4. Если кандидатов нет — в оба поля пишется
   `# Нет файлов для выгрузки.` и выход.
5. Иначе:
   - Удалённая папка: `remote_base + "/" + сегодня + "/"`.
   - `dst = "<user>@<host>:<remote_dir>"`.
   - Собирается строка `scp "<путь 1>" "<путь 2>" ... <dst>`.
     Пути с пробелами оборачиваются в кавычки.
6. В поле «Команда для копирования» — только эта строка.
7. В поле «Информация о файлах» — строки `#` по каждому файлу.
8. Список имён сохраняется во внутреннее поле `_pending_upload` —
   его использует «Отметить выгрузку выполненной».

`scp` **не запускается**, ни `subprocess`, ни через `os.system`.

### 6.14. Копирование команды (`copy_upload_cmd`)

- Берёт содержимое поля «Команда для копирования».
- Если пусто или начинается с `#` — сообщение «сначала сформируйте
  команду».
- Иначе `root.clipboard_clear()` + `clipboard_append(...)` и
  сообщение «Команда скопирована в буфер обмена».

### 6.15. Отметка выгрузки (`mark_uploaded`)

- Если `_pending_upload` пуст — сообщение «сначала сформируйте команду».
- Иначе для каждого имени из `_pending_upload` записывается
  сегодняшняя дата в `server_upload_log[name]`.
- Конфиг сохраняется, показывается число отмеченных файлов,
  `_pending_upload` обнуляется.

Смысл: после ручного выполнения `scp` в терминале вы жмёте эту кнопку,
и при следующем формировании команды уже выгруженные файлы не попадут
в список (пока не появится архив с более свежей датой).

### 6.16. Стартовое сканирование (`startup_scan`)

- Вызывается из `App.__init__` через `root.after(150, ...)` — после
  того, как окно отрисовано (иначе tkinter может «залипнуть» на
  диалогах до `mainloop`).
- Сначала `scan_extensions(silent=True)`, затем `scan_files(silent=True)`.
- Оба сохраняют конфиг после ответов пользователя.

### 6.17. Что приложение **не делает**

- Не вызывает `git`.
- Не вызывает `scp`.
- Не создаёт сетевых соединений.
- Не пишет файловых логов — только окна UI.
- Не рекурсирует по подпапкам — работает только с корнем `folder`.
- Не удаляет и не изменяет исходные файлы.
- Не открывает `.xlsx` и не читает его ячейки — только метаданные
  (размер, mtime). Формулы, значения, форматирование для сравнения
  не используются.
- Не пытается определить «бинарность» текстовых файлов — читает
  только те, что пользователь явно выбрал как обрабатываемые и что
  не входят в `binary_meta_extensions`.
