# План восстановления

## Статус системы P&R на текущем этапе

P&R развивается постепенно. Описание механизма в документации само по себе не означает, что механизм уже реализован и используется.

На текущем этапе необходимо различать:

1. **Работает** — механизм реально используется в повседневной жизни.
2. **Эксперимент** — механизм уже реализуется и проверяется на практике.
3. **Будущее** — идея или механизм, который пока не внедряется.
4. **Не работает** — механизм был опробован, но не дал требуемого результата.
5. **Мёртвый груз** — элемент существует только в документации и не выполняет полезной функции.

### Основные работающие элементы P&R

На текущем этапе реально используются:

* роли и подроли;
* приоритизация задач;
* общий список задач;
* Sprint;
* выделение задач текущего Sprint;
* ежедневное планирование;
* фиксация фактически выполненных действий в `Actions`;
* связь `Task → Action`;
* возможность связывать Action непосредственно с Epic;
* возможность фиксировать Action без заранее заданной задачи;
* фиксация сна;
* фиксация физической активности;
* утренний блок и другие работающие процедуры/рутины.

### Приоритет задач

Вместо первоначального ручного механизма ABCDE сейчас используется вычисляемый приоритет.

Priority Score учитывает свойства задачи, в частности:

* категорию приоритета;
* дедлайн;
* объём задачи.

Текущая формула является рабочим механизмом системы и используется для автоматического упорядочивания задач.

ABCDE ранее использовался как временный ручной механизм приоритизации. Он не является текущим основным механизмом P&R.

### Sprint

Общий список задач является Backlog.

Для работы на ограниченном периоде из Backlog формируется отдельный Sprint.

Большой Backlog не является ежедневным рабочим списком.

В течение Sprint основная работа ведётся с выбранным набором задач Sprint.

### Actions

`Actions` предназначен для фиксации того, что фактически было сделано.

Основная задача текущего этапа:

> **не потерять информацию о реально совершённых действиях и использовать её для последующего анализа и планирования.**

Action может быть связан:

* с Task;
* с Epic;
* либо не иметь связи с заранее существовавшей задачей или Epic.

На практике большая часть действий в текущей системе оказывается связана с задачами.

### Results

`Results` пока не является обязательным рабочим механизмом.

Закладка/лист `Results` сохраняется как задел для дальнейшего развития системы.

В перспективе Results может использоваться для фиксации значимых результатов, в том числе при завершении Sprint или во время Review.

Пока не требуется регистрировать Result после каждого Action.

### Связь Epic / Task / Action

На текущем этапе используется следующая модель:

> **Epic → Task → Action**

Однако Action не обязан иметь Task:

> **Epic → Action**

или:

> **Action**

если действие было незапланированным и не относилось к существующему Epic или Task.

Связь `Epic/Task → Action` не должна рассматриваться как жёсткая последовательность заранее запланированных действий.

План описывает намерение, а не обязанность воспроизвести заранее известную последовательность действий.

В процессе выполнения задачи фактические действия могут отличаться от первоначального плана.

Задача также может изменяться после получения новой информации.

На текущем этапе P&R не требует отдельного хранения истории редактирования задач.

Если формулировка незавершённой задачи изменилась вследствие полученной информации, задача может быть отредактирована.

При этом уже записанные Actions сохраняются и продолжают ссылаться на ту задачу, с которой они были связаны на момент выполнения.

### Текущий фокус развития

Сейчас главная задача P&R — не анализировать отклонения фактических действий от первоначального плана.

Главная задача:

> **научиться надёжно фиксировать фактически совершённые действия и не терять информацию о том, что реально было сделано.**

Поэтому на текущем этапе:

* не требуется обязательная фиксация каждого результата;
* не требуется анализировать каждое отклонение от плана;
* не требуется восстанавливать полную историю изменения задач;
* не требуется связывать каждое действие с заранее существовавшей задачей;
* не требуется создавать сложную систему учёта.

Сначала необходимо накопить реальный массив данных о действиях.

В дальнейшем эти данные могут использоваться для:

* анализа поведения;
* планирования следующих действий;
* анализа связи между условиями, действиями и результатами;
* поиска закономерностей, например между сном, физической активностью, условиями дня и эффективностью работы.

# Иерархия работы P&R

Текущая модель:

> **Initiative → Epic → Task → Action**

При этом уровни имеют разный смысл.

### Initiative

Будущий уровень иерархии над Epic, предназначенный для объединения нескольких связанных Epic.

На текущем этапе отдельная сущность Initiative не реализуется.

Принадлежность Epic к Initiative определяется ментально или, при необходимости, через справочный лист без рабочих связей.

### Epic

Значимый крупный результат или крупный объём работы, который объединяет несколько связанных задач.

### Task

Конкретная единица работы, которую необходимо выполнить для достижения результата Epic либо которая сама по себе содержит результат и действия.

### Action

Фактически совершённое действие.

Action фиксирует не намерение, а то, что реально произошло.

# Sprint

Общий Backlog содержит задачи, которые потенциально могут быть выполнены.

Sprint является ограниченным рабочим набором задач на конкретный период.

В начале Sprint из Backlog выбираются задачи, которые предполагается выполнять в течение Sprint.

При этом выбор задач Sprint не означает, что первоначальный список является неизменным обязательством.

По мере получения новой информации задачи могут:

* уточняться;
* изменяться;
* разбиваться;
* заменяться;
* переноситься;
* становиться ненужными;
* дополняться новыми задачами.

Sprint нужен прежде всего для того, чтобы ограничить объём текущей работы и не заставлять человека ежедневно работать с огромным общим Backlog.

# Организация задач в блоки

### Задача и блок задач

**Задача** — отдельная логическая единица работы, которую можно выполнить и завершить как самостоятельное действие.

**Блок задач** — несколько связанных задач, объединённых общей целью и/или последовательностью выполнения, которые в данном контексте рассматриваются и выполняются как единое целое.

Блок задач может включать задачи, относящиеся к разным ролям.

### Правило отнесения блока задач к роли

Если блок состоит из нескольких неразрывно связанных задач, относящихся к разным ролям, блок относится к той роли, для которой выполнение всего блока в целом является способом достижения её основного результата.

Для выбора роли-владельца дополнительно можно использовать вопросы:

1. Для достижения какого результата какой роли предназначен блок в целом?
2. Если убрать весь блок, какой роли будет нанесён наибольший ущерб?

Отдельные задачи внутри блока при этом могут обеспечивать результаты других ролей.

# Обязательные результаты

## Сон

* Восстановить нормальный режим сна.
* Не проводить ночь без сна.
* Не компенсировать ночной недосып длительным дневным сном.

## Здоровье

* Ежедневно выйти из дома и погулять.
* Поддерживать базовую физическую активность.
* Нормально питаться.

## Работа

* Выполнить обязательные рабочие задачи.
* Не допускать накопления новых просроченных задач.
* В первую очередь закрывать задачи, последствия невыполнения которых уже проявились.

## Питание

* Обеспечить себя подходящей едой на ближайшие дни.
* Обеспечивать регулярный приём пищи.
* Не допускать ситуации, когда отсутствие еды приводит к хаотичному питанию.

## Быт

* Привести в приемлемое состояние основные зоны квартиры.
* Обеспечить чистую посуду и необходимую чистую одежду.
* Не пытаться сделать генеральную уборку.

## Возвращение к приоритетам

* Каждый день определить главное дело или главный результат дня.
* После срыва возвращаться к действиям как можно быстрее, не дожидаясь нового «идеального старта».
* Не пытаться компенсировать несколько потерянных дней чрезмерной нагрузкой.

# Правила на текущий этап

* Не пытаться восстановить всю жизнь сразу.
* Не начинать новые крупные проекты.
* Не совершенствовать систему планирования вместо выполнения реальных дел.
* Сначала выполнять действительно важные и обязательные задачи.
* Всё необязательное переносить, если оно мешает восстановлению базы.
* Не пытаться компенсировать прошлые неудачи чрезмерным количеством задач.
* После каждого дня оценивать состояние и при необходимости корректировать план.
* **Срыв отдельного дня не считать причиной прекращать план: на следующий день просто возвращаться к минимальному режиму.**
