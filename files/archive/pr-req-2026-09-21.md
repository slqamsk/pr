# ТЗ: веб-приложение Plans&Results

### 1. Стек
**MySQL + PHP API + HTML/PHP + CSS + JavaScript.**

### 2. Сущности
**Role**
* `id`
* `name`
* `description`

**Action**
* `id`
* `date`
* `name`
* `role_id`
* `planned` — boolean
* `importance` I — `1..5`
* `difficulty` D — `1..5`
* `novelty` N — `0..3`
* `pomodoros` T — количество одинарных помидорок
* `productivity` P — `0..1`, nullable
* `completed` — boolean
* `points`

### 3. Расчёт
Базовые баллы:
> **B₀ = I + D + I×D + N**

Количество одинарных помидорок:

> **T = ⌈время / 25 мин⌉**

Если `T ≤ 2`:

> **B = B₀**

Если `T > 2`:

> **B = B₀ × (T / 2) × P**

где `P ∈ (0; 1]`.

### 4. Короткие действия

Для действий, не требующих времени:

> **T = 2, P не учитывается.**

Таким образом, «вовремя лечь спать» получает полный `B₀`, хотя затраты времени ≈ 0.

### 5. Выполнение

Баллы начисляются только при:

> `completed = true`

### 6. День

Для каждой даты:

> **DayPoints = Σ B**

### 7. Интерфейс

* список действий за день;
* добавление/редактирование действия;
* автоматический расчёт баллов;
* итоговые баллы дня;
* график **DayPoints по дням**;
* 7-дневное скользящее среднее.

### 8. Эксперимент

Хранить исходные `I, D, N, T, P`, а не только `B`.

Формулу расчёта вынести отдельно, чтобы можно было пересчитать историю при изменении модели.

---

### Один нюанс, который я бы **обязательно обсудил до программирования**

В твоей формуле для длинного действия получается, например:

> `T = 3` помидорки = 75 минут
> `T / 2 = 1,5`

То есть действие получает **1,5 × B₀ × P**.

Это математически нормально и, на мой взгляд, даже лучше, чем снова округлять до часов.

Но тогда возникает красивое свойство:

> 25 минут → 1×B₀
> 50 минут → 1×B₀
> 75 минут → 1,5×B₀
> 100 минут → 2×B₀
> 125 минут → 2,5×B₀

То есть **первые две помидорки — базовая награда, дальше баллы растут пропорционально времени и корректируются продуктивностью**.

## Часть 1. Бизнес-требования (MVP)

### 1.1. Цель
Создать персональный инструмент для учёта и оценки выполненных действий, мотивирующий пользователя на реализацию жизненных ролей. На первом этапе система позволяет фиксировать действия с их ключевыми параметрами (важность, сложность, новизна, затраченное время, продуктивность) и управлять их состоянием. MVP даёт возможность вести учёт действий, управлять ролями и видеть структуру своей активности по дням.

### 1.2. Функциональные требования (MVP)

#### 1.2.1. Роли (жизненные сферы)
- Пользователь создаёт **роли** (например, «Управляющий здоровьем», «Финансовый обеспечитель»).
- Роли можно создавать, редактировать, удалять.

#### 1.2.2. Действия
- Действие относится к определённой дате.
- Действие может быть привязано к роли, но это **не обязательно** (`role_id` может быть NULL).
- Действие имеет **статус** (`status`), который может принимать одно из трёх значений:
  - `active` – действие активно, не запланировано, не завершено.
  - `planned` – действие запланировано, но ещё не выполнено.
  - `completed` – действие выполнено.
- Действие имеет **происхождение** (`origin`), которое показывает, как оно попало в систему:
  - `planned` – действие было запланировано заранее.
  - `forgotten` – действие не было запланировано, но должно было быть выполнено (пользователь осознаёт, что забыл его запланировать).
  - `spontaneous` – действие добавлено в течение дня, потому что появилась новая информация или изменились обстоятельства.
- Для действия задаются:
  - `importance` (Важность) – от 1 до 5
  - `difficulty` (Сложность) – от 1 до 5
  - `novelty` (Новизна) – от 0 до 3
  - Время:
    - `duration_minutes` – затраченное время в минутах (целое, может быть NULL)
    - `pomodoros` – затраченное время в количестве помидорок (целое, может быть NULL)
    - Одно из этих двух полей должно быть заполнено, если действие не является коротким.
  - `productivity` (Продуктивность) – число от 0,00 до 1,00 (по умолчанию 1,00), используется для длительных действий.
  - `is_short` – признак короткого действия (не требующего учёта времени).
- Действие может быть создано, отредактировано, удалено.
- Статус и происхождение могут быть изменены в любой момент.

#### 1.2.3. Отображение
- Пользователь видит список действий за выбранный день.
- Действия группируются по статусу: сначала `active` и `planned`, затем `completed` (или наоборот, по усмотрению интерфейса).
- Для каждого действия отображаются все введённые параметры, включая статус и происхождение.

## Часть 2. Техническая реализация (MVP)

### 2.1. Стек технологий
- **База данных:** MySQL
- **Backend:** PHP (нативное API)
- **Frontend:** HTML + CSS + JavaScript (SPA-подход)
- **Формат обмена:** JSON

### 2.2. Аутентификация и авторизация
- Регистрация и вход по логину и паролю.
- Пароли хранятся в хешированном виде.
- После входа выдаётся **токен** (случайная строка, сохраняется в БД).
- Все запросы к API требуют заголовок `Authorization: Bearer <token>`.
- Данные разных пользователей изолированы через `user_id`.

### 2.3. Структура базы данных
```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    login VARCHAR(50) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    token VARCHAR(255) NULL
);

CREATE TABLE roles (
    id INT AUTO_INCREMENT PRIMARY KEY,
    user_id INT NOT NULL,
    name VARCHAR(100) NOT NULL,
    description TEXT,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE actions (
    id INT AUTO_INCREMENT PRIMARY KEY,
    user_id INT NOT NULL,
    date DATE NOT NULL,
    name VARCHAR(255) NOT NULL,
    role_id INT NULL,
    status ENUM('active', 'planned', 'completed') DEFAULT 'active',
    origin ENUM('planned', 'forgotten', 'spontaneous') DEFAULT 'spontaneous',
    importance INT NOT NULL CHECK (importance BETWEEN 1 AND 5),
    difficulty INT NOT NULL CHECK (difficulty BETWEEN 1 AND 5),
    novelty INT NOT NULL CHECK (novelty BETWEEN 0 AND 3),
    duration_minutes INT NULL,
    pomodoros INT NULL,
    productivity DECIMAL(3,2) DEFAULT 1.00,
    is_short BOOLEAN DEFAULT FALSE,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    FOREIGN KEY (role_id) REFERENCES roles(id) ON DELETE SET NULL
);

CREATE INDEX idx_actions_user_date ON actions(user_id, date);
CREATE INDEX idx_actions_user_role ON actions(user_id, role_id);
```

> **Валидация на уровне приложения:**
> - Если `is_short = false`, то обязательно, чтобы `duration_minutes > 0` или `pomodoros > 0`. Если оба NULL или 0 – ошибка 400.
> - Если `is_short = true`, то `duration_minutes` и `pomodoros` должны быть NULL.

### 2.4. Спецификация API (REST)

**Базовый путь:** `/api/v1/`

#### Авторизация
- **POST /auth/register** – регистрация. Тело: `{ "login", "password" }`. Ответ: `{ "token" }` при успехе.
- **POST /auth/login** – вход. Тело: `{ "login", "password" }`. Ответ: `{ "token" }` при успехе.
- **POST /auth/logout** – выход (требуется токен). Ответ: `{ "success": true }`.

#### Роли (требуется токен)
- **GET /roles** – список всех ролей пользователя. Ответ: массив объектов с полями `id`, `name`, `description`.
- **POST /role** – создание роли. Тело: `{ "name", "description" }`. Ответ: `{ "id" }`.
- **PUT /role/{id}** – обновление роли. Тело: `{ "name", "description" }`. Ответ: `{ "success": true }`.
- **DELETE /role/{id}** – удаление роли. Ответ: `{ "success": true }`.

#### Действия (требуется токен)
- **GET /actions?date=YYYY-MM-DD** – получить все действия за указанную дату. Ответ: массив объектов с полями: `id`, `date`, `name`, `role_id` (или null), `status` ('active', 'planned', 'completed'), `origin` ('planned', 'forgotten', 'spontaneous'), `importance`, `difficulty`, `novelty`, `duration_minutes`, `pomodoros`, `productivity`, `is_short`.
- **POST /action** – создать действие. Тело: `{ "date", "name", "role_id" (или null), "status" (опционально, по умолчанию 'active'), "origin" (опционально, по умолчанию 'spontaneous'), "importance" (1-5), "difficulty" (1-5), "novelty" (0-3), "duration_minutes" (или null), "pomodoros" (или null), "productivity" (0-1, опционально), "is_short" (bool) }`. Ответ: `{ "id" }`.
- **PUT /action/{id}** – обновить действие. Тело: те же поля, что и при создании, плюс `status` и `origin`. Ответ: `{ "success": true }`.
- **DELETE /action/{id}** – удалить действие. Ответ: `{ "success": true }`.

## Часть 3. Планы на последующие версии

### Версия 2 (расчёт баллов и графика)
- Реализация расчёта баллов по следующей формуле:
  - **Базовые баллы** = Важность + Сложность + Важность * Сложность + Новизна
  - **Количество помидорок (T)**:
    - Одна помидорка = 30 минут (включая активную работу и перерывы).
    - Если действие короткое (`is_short = true`), то `T = 2`.
    - Иначе `T` определяется из `duration_minutes` (приоритет) или `pomodoros`.
    - Если оба поля времени не заполнены – ошибка валидации (уже реализована в MVP).
  - **Итоговые баллы**:
    - Если `T <= 2`: баллы = базовые.
    - Если `T > 2`: баллы = базовые * (T / 2) * продуктивность.
- Добавление вычисляемого поля `points` в ответе `GET /actions` (для действий со статусом 'completed').
- Добавление эндпоинта `GET /stats` для получения суммы баллов по дням (агрегация по завершённым действиям).
- Отображение графика `DayPoints` на фронтенде.
- Отображение баллов рядом с каждым завершённым действием.
- (Опционально) 7-дневное скользящее среднее на графике.
